SQL Analytics

Twelve SQL queries that turn a year of pizza orders into decisions a manager can act on.

Open the repositorySkip to the problem

Problem

An order log does not tell a manager what to cut, when to staff or what is growing. Each query here answers one of those decisions.

What it does

  • Loads 21,350 orders and 48,620 order lines into a normalised DuckDB schema.
  • Runs 10 data-quality checks before any analysis.
  • Answers menu, staffing, size mix, growth and basket questions in 12 SQL files.
  • Saves every result as CSV and draws Pareto, heatmap, trend and size-mix charts.

Architecture

No server: one Python process opens an in-memory DuckDB, loads the CSVs, runs every SQL file and writes CSVs and charts to disk. Tests build their own database from a 12-order fixture.

How it works

  1. Download

    Fetch the public Pizza Place Sales zip and convert one Windows-1252 file to UTF-8.

  2. Create schema

    Four tables with keys, CHECK rules, decimal prices, indexes and a joined sales view.

  3. Load

    Read the CSVs with explicit column types, parents first so every foreign key holds.

  4. Run queries

    Execute every numbered SQL file in order; window functions, CTEs and a generated calendar.

  5. Save and chart

    Write each result to CSV, then draw four charts in light and dark versions.

  6. Test

    pytest checks every query against a hand-made fixture with known answers.

Design decisions

  • Fixed a growth query that compared a full week with a 4-day week, a false +62%.
  • Tests check answers against a fixture with known results, not just column names.
  • A new question is just a new SQL file; the runner needs no code change.
